Kalibracja „<5” dla lat 2017–2018, bez zestawienia świadczeń

Metoda v4 opiera komórkę na dwóch źródłach z zestawienia świadczeń: punktach i liczbie pacjentów. Zestawienie ma dane od 2019 r. Ten dokument opisuje, co możemy zrobić dla lat 2017–2018, jak to sprawdzić przed wdrożeniem i jakie są ryzyka.

Wyniki testu wstecznego: test-wsteczny-2022-2023.html. Powiązane: schemat metody v2/v4, plan kalibracji, roadmapa.

2. Co z v4 zostaje, a co znika

  • Zostaje: granice z pliku (lo, hi), cele zakresów i suma grupy z API, przydział zgonów (z zasadą „pobyt w wierszu ze zgonem jest zgonem”), histogram dni.
  • Znika: wszystko, co rozróżnia szpitale wewnątrz zakresu: pacjenci (metoda A, dolna granica, hi2) i punkty (metoda B). Bez tego v4 nie wie, czy wiersz „<5” w szpitalu X to raczej 1, czy raczej 3 pobyty.
  • Wniosek: potrzebujemy innego źródła różnic między szpitalami. Mamy dwa kandydaty: atrybuty wierszy w połączeniu z rozkładami krajowymi z API (wariant 1) i strukturę tych samych komórek z lat 2019+ (wariant 2).

3. Wariant 1: dopasowanie do wszystkich rozkładów krajowych z API

Każdy wiersz „<5” dostaje wartość od 1 do 4. Szukamy wartości, przy których sumy pliku zgadzają się jednocześnie z kilkoma tabelami API dla grupy:

  • suma grupy i pobyty w zakresach umów (jak w v4),
  • zgony (tryb wypisu 9),
  • długość pobytu w 4 przedziałach (z histogramu dni),
  • tryb przyjęcia (te same kody co w pliku),
  • płeć,
  • wiek: tylko tam, gdzie granice grup da się złożyć (API: 18–40, 41–60, 61–80, 81+; plik: 18–44, 45–64, 65+) — zwykle tylko podział dzieci / dorośli.

Technika: iteracyjne dopasowanie proporcjonalne (raking, IPF) z obcięciem do [1, 4] na wiersz. Start: 1 na wiersz (min) albo wartości z wariantu 2. Po każdym obrocie po tabelach wartości mnożymy, żeby zgodzić się z kolejną tabelą, i obcinamy do granic. Na końcu zaokrąglamy z zachowaniem sum (jak w v4).

Co to daje: szpital, który ma dużo wierszy „<5” w kategoriach niedoszacowanych przez min (np. długie pobyty, tryb nagły), dostaje więcej pobytów. To realna informacja, bo API mówi, gdzie brakuje pobytów.

Ograniczenie: dwa szpitale z wierszami o tych samych atrybutach dostaną tę samą wartość. Różnice między szpitalami wynikają tylko z miksu wierszy.

4. Wariant 2: struktura komórki z lat z zestawieniem

Dla komórki liczymy z v4 (2019 r., docelowo średnia 2019 i 2021–2022, z pominięciem 2020 przez COVID) nadwyżkę na wiersz „<5”: (cal − min) ÷ liczba wierszy „<5”. Zakładamy, że ten sam szpital w tym samym zakresie i produkcie ma podobny profil pacjentów rok czy dwa lata wcześniej.

start(wiersz 2018) = 1 + nadwyżka na wiersz komórki w 2019 · (popr. do sumy zakresu z API 2018)
  • 85–90% wierszy „<5” z 2017–2018 ma komórkę w 2019 r. Pozostałe dostają średnią zakresu albo grupy.
  • Produkty spoza katalogu 2019 (ok. 6% wierszy) nie mają odpowiednika. Zostają przy wariancie 1.
  • Zmiany kodów zakresów i NIP między latami trzeba połączyć tak jak w v4 (lista ręczna kodów świadczeniodawców).

Ryzyko: zmiana katalogu JGP. Przykład: E10 do września 2017 r. obejmowało więcej przypadków (punkt kontrolny E10 2017: 20 596 pobytów min, 2018: 10 431). Struktura komórki z 2019 r. może wtedy nie pasować. Takie produkty trzeba wykryć (np. duża zmiana liczby wierszy komórki między latami) i dać im wariant 1.

5. Rekomendacja: wariant 2 jako start, wariant 1 jako dopasowanie

  1. Start: wartości wierszy z wariantu 2 (struktura komórek z 2019+), dla komórek bez odpowiednika 1 + średnia nadwyżka zakresu.
  2. Dopasowanie: raking z wariantu 1 do tabel API 2017/2018: zakresy, suma grupy, zgony, długość pobytu, tryb przyjęcia, płeć. Raking zmienia start możliwie mało (minimalna odległość od startu, mnożniki zamiast nowych wartości).
  3. Granice: twarde [1, 4] na wiersz, suma grupy = API, wiersz ze zgonem zawiera tylko zgony.
  4. Oznaczenie: w danych metoda cal-2017 (inna niż v4), w UI informacja, że dla 2017–2018 szacunek jest mniej pewny.

Ta kombinacja to jedna zasada, a nie zestaw wyjątków: każdy rok ma start (z danych szpitala, jeśli są) i dopasowanie do wszystkich tabel API. Dla lat 2019+ ten sam raking można później dodać jako krok po v4 (dopasowanie rozkładów krajowych, które v4 teraz tylko sprawdza).

6. Jak to sprawdzimy przed wdrożeniem: test wsteczny

Liczymy metodę dla roku, w którym mamy pełne v4, udając, że nie mamy zestawienia. Wynik porównujemy z v4.

TestRok testuStart z rokuCo sprawdza
A20232024 (1 rok różnicy)jak 2018 ← 2019
B20222024 (2 lata)jak 2017 ← 2019
C2023bez startu (sam wariant 1)ile daje sam raking

Miary: pobyty przesunięte względem v4 (%), błąd komórki (mediana, 90. percentyl), test zakresów bez celów z API, udział komórek, w których wynik leży bliżej v4 niż min i sim. Kryterium wdrożenia: metoda musi być wyraźnie bliżej v4 niż min i sim w każdym teście; inaczej dla 2017–2018 zostaje min z jasną informacją.

Rozkłady krajowe z API nie są w tym teście niezależne (raking je dopasowuje), dlatego główną miarą jest odległość od v4 na poziomie komórek. Pary lat po 2021 r. wybieramy celowo: omijają COVID (2020–2021), a w latach 2022–2024 mamy pełne v4.

Czy test jest reprezentatywny? Przetasowania między latami

Sumy krajowe dla każdej grupy JGP mamy z API dokładnie dla każdego roku. Niewiadomą jest tylko podział między szpitale wewnątrz grupy, a ten zmienia się z roku na rok (szpital przejmuje pacjentów, inny zamyka oddział). Test wsteczny mierzy właśnie ten błąd, pod warunkiem że przetasowania w parze testowej są podobne jak między 2017–2018 a 2019. Plik hospitalizacji mamy dla wszystkich lat, więc da się to porównać wprost (pobyty metodą min w komórkach):

Przetasowania w parach testowych są takie same jak w parach docelowych (przy tej samej odległości w latach). Różni się tylko pokrycie: w 2017–2018 więcej wierszy leży w komórkach, których nie ma w roku startu (zmiana katalogu JGP w 2017 r., zmiany zakresów). Test wsteczny będzie więc trochę zbyt optymistyczny dla komórek bez odpowiednika; ich błąd trzeba podać osobno.

Przetasowanie = ½ Σ |udział komórki w grupie w roku A − udział w roku B| po komórkach obecnych w obu latach (mediana po grupach JGP; ważone pobytami). Liczone na pobytach metodą min.

7. Otwarte pytania i ryzyka

  • Pobranie API 2017–2018 dla wszystkich produktów (fetch_jgp_stats.py --years 2017-2018): sprawdzone dla E10, trzeba potwierdzić pokrycie produktów z katalogu 2017.
  • Nazwy zakresów w API 2017–2018 a w pliku: w v4 łączymy po nazwie z zestawienia; bez zestawienia trzeba słownika kod zakresu → nazwa (np. z plików 2019+ albo z API umów NFZ).
  • Wykaz procedur ICD-9 per szpital i grupa JGP (dane.gov.pl, zbiór 3009 „Dane dotyczące hospitalizacji rozliczonych JGP”, plik procedur „w latach 2019–2021”, 7z, 117 MB). Plik hospitalizacji z tego samego zbioru, opisany jako 2019–2021, zawiera też lata 2017–2018 — możliwe, że plik procedur także. Liczba procedur w szpitalu i grupie JGP byłaby sygnałem wielkości komórki, którego brakuje bez zestawienia. Do pobrania i sprawdzenia.
  • Inne źródła sprawdzone (7.11.2026): ezdrowie.gov.pl „Liczba hospitalizacji i wartość ich refundacji w ramach JGP według świadczeniodawców” — dopiero od 2020 r.; „Informacje o liczbie hospitalizacji sprawozdanych dla wybranych grup JGP” — 2019–2021; „Miesięczny raport dot. hospitalizacji JGP” — od 2020 r., bez podziału na szpitale; mapy potrzeb zdrowotnych (BASiW) — oddziały, nie szpitale i grupy JGP; zbiór 4514 — tylko szpitale samorządu województwa śląskiego.
  • API umów NFZ (mamy próbkę data/nfz_umowy_09R_010019.json): umowy szpitala z planem w zakresach. Do sprawdzenia, czy są dla 2017–2018 i czy wartość umowy w zakresie może zastąpić punkty jako sygnał różnic między szpitalami.
  • Wiek: granice grup w API i w pliku się nie pokrywają; używamy tylko tego, co da się złożyć.
  • Zmiana katalogu w październiku 2017 r.: produkty, które zmieniły zakres, wymagają osobnego traktowania (wariant 1 bez startu).
  • Zgony: te same zasady co w v4; w latach z dużą liczbą zgonów w wierszach „<5” sprawdzić, czy suma zgonów nie odbiega od API bardziej niż w 2024 r. (+67, 0,04%).

8. Kroki

  1. Pobrać tabele API dla 2017–2018 (lata testowe 2022–2024 są już pobrane i policzone v4).
  2. Policzyć v4 dla 2019 (start dla 2017–2018) — wymaga tabel API 2019.
  3. Napisać raking (wariant 1) jako osobną funkcję z testami na małych danych.
  4. Test wsteczny A–C, raport w tym folderze.
  5. Decyzja: wdrożenie dla 2017–2018 albo zostawienie min.
